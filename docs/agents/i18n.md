# Internationalization (i18n) reference

Canonical reference for translating OpenPorte. The **`.po` files under`languages/` are the
source of truth** — there is no separate dictionary or build step. The toolchain is WP-CLI
(`wp i18n make-pot`) to extract the template, plus GNU gettext (`msgmerge`, `msgfmt`) to sync
and compile. See `AGENTS.md` → "i18n discipline" for the rules
that apply while *writing* code (wrapping strings, `translators:` comments); this document
covers *producing and maintaining* the translations.

## Current state

Thirty locales ship under `languages/`, in two deliberate tiers:

- **Fully translated (14):** `cs_CZ`, `de_DE`, `es_ES`, `fr_FR`, `it_IT`, `ja`, `nl_NL`,
  `pl_PL`, `pt_PT`, `ro_RO`, `tr_TR`, `uk`, `xh_ZA`, `zh_CN`
  every string, admin screens included.
- **Visitor-strings only (20):** the rest (e.g. `fi`, `ru_RU`, `sv_SE`, …). Only the
  six widget-facing strings a site visitor sees (the `get_translations()` set in
  `includes/core.php`: label, verified/verifying states, wait alert, error, footer) are
  translated; admin strings intentionally fall back to English. When a release adds or
  rewords a *visitor-facing* string, this tier must be refreshed too — admin-string gaps
  here are by design, not debt.

## Prerequisites

- [WP-CLI](https://wp-cli.org/) with the i18n command (`wp i18n make-pot`) — used only to extract
  the `.pot` template from the PHP source.
- GNU gettext (`msgmerge`, `msgfmt`) to sync, validate and compile. On macOS: `brew install gettext`.

## The toolchain (single source of truth)

```bash
# 1. Regenerate the POT template from the source code
wp i18n make-pot . languages/openporte.pot \
  --domain=openporte \
  --exclude=vendor,local,tests,public/altcha.min.js \
  --slug=openporte

# 2. Sync every locale's .po against the new template (fuzzy-matching merge).
#    A brand-new string lands with an empty msgstr; a reworded or typo-fixed msgid
#    KEEPS its old translation, now flagged "#, fuzzy" with a "#| msgid" line recording
#    the previous source text. Nothing is lost.
for po in languages/openporte-*.po; do
  msgmerge --update --backup=none --previous "$po" languages/openporte.pot
done

# 3. Stamp the release version into the .po headers (replace X.Y.Z).
sed -i '' \
  's/Project-Id-Version: OpenPorte Spam Protection [0-9.]*/Project-Id-Version: OpenPorte Spam Protection X.Y.Z/' \
  languages/openporte-*.po
# On Linux, drop the '' after -i.

# 4. Compile the .mo binaries WordPress actually loads.
#    msgfmt EXCLUDES "#, fuzzy" entries by default, so a not-yet-reviewed string falls
#    back to English at runtime until a translator removes the flag. --check also gates
#    on syntax + placeholder errors, so this validates AND builds in one pass.
for po in languages/openporte-*.po; do
  msgfmt --check "$po" -o "${po%.po}.mo"
done
```

`msgmerge`/`msgfmt` operate on one `.po` at a time (the retired `wp i18n` commands took a whole
directory — hence the loops). To touch a single locale, run them directly, e.g.
`msgmerge --update --backup=none --previous languages/openporte-fr_FR.po languages/openporte.pot`.

> **Why GNU gettext and not `wp i18n update-po` / `make-mo`?** Those two WP-CLI commands cannot
> deliver the fuzzy workflow: `update-po` does *exact* `msgid` matching, so a one-character source
> fix (e.g. `Wordpress` → `WordPress`) drops the old entry and re-adds an empty one — the
> translation is **lost**. And `make-mo` compiles `#, fuzzy` entries *into* the `.mo`, so a stale
> translation would ship instead of the English fallback. `msgmerge` (similarity matching, keeps +
> flags the translation) and `msgfmt` (skips fuzzy by default) are the reference implementations and
> give exactly the "preserve, mark to-update, show English meanwhile" behaviour. `wp i18n make-pot`
> stays — it is the one genuinely WordPress-aware step (it understands `__()`, `esc_html__()`, …).

### Adding a new language to the list of translations

After the regeneration of the POT template from our toolchain standard workflow, you can insert
the following steps:

```bash
# 2-bis. Create the new language .po file by copying the .pot
cp languages/openporte.pot languages/openporte-*.po
# e.g.: cp languages/openporte.pot languages/openporte-xh_ZA.po

# 2-bis.1. Edit the .po header — at minimum set these fields by either adding or updating them (for plural forms, the (Unicode CLDR plural rules)[https://unicode-org.github.io/cldr-staging/charts/latest/supplemental/language_plural_rules.html] is the authoritative reference):
#    "Language: <language[_territory]>\n"
#    "PO-Revision-Date: <date>\n"
#    "Last-Translator: <name>\n"
#    "Language-Team: <Language_name>\n"
#    "Plural-Forms: nplurals=2; plural=(n != 1);\n"

# 2-bis.2. Translate the strings in the .po file
# (by hand, or feed it to a translator/LLM)
```

## Glossary — terms to preserve verbatim

Never translate these (leave `msgstr` identical to `msgid`, or keep the term inline in a longer
string):

**Brand / plugin / theme names:** OpenPorte, OpenPorte Spam Protection, ALTCHA,
ALTCHA Spam Protection, WordPress / Wordpress, WooCommerce, Contact Form 7, Gravity Forms,
Forminator, Formidable Forms, Elementor Pro Forms, CoBlocks, wpDiscuz, WPForms, HTML Forms,
Enfold Theme, Custom HTML, Shortcode.

**Technical terms:** CAPTCHA, JavaScript, GDPR, GitHub, REST API, HMAC, PoW / proof-of-work,
PHP, WP-CLI, GPL.

**Always preserve exactly, in every language:**

- URLs (`http://…`, `https://…`).
- Placeholders: `%s`, `%d`, `%1$s`, `%2$s`, … — same set, same order semantics.
- HTML tags: `<a>`, `<b>`, `</a>`, … — same tags, unchanged.

> Some terms have an accepted local form (e.g. *CAPTCHA* may stay, but "proof-of-work" can be
> explained). When in doubt, prefer the English term over an awkward coinage.

## Quality rules

- **Accuracy** — natural and idiomatic in the target language; keep the source's level of formality.
- **Consistency** — translate a given term the same way everywhere; reuse existing choices in the
  same `.po` before inventing new ones.
- **Completeness** — every translatable string gets a `msgstr`; empty `msgstr` should be rare. If
  genuinely unsure, leave the English text rather than guessing.
- **Comments** — keep every `#. translators:` comment. Any string with a placeholder should have one.

## Procedure: refresh a language after code changes

Use when source strings were added/changed (the i18n discipline flagged it in a commit). Example: `fr_FR`.

1. Regenerate the template and sync — steps 1–2 above. New strings land empty; reworded strings
   become `#, fuzzy` (the old translation is kept as a suggestion).
2. Fill the gaps: translate every empty `msgstr`, review each `#, fuzzy` entry, and **remove the
   `fuzzy` flag** once corrected. This is the natural place to hand the file to a local LLM (below).
3. Validate + compile in one step: `msgfmt --check languages/openporte-fr_FR.po -o languages/openporte-fr_FR.mo`
   (0 errors required; fuzzy entries are excluded from the `.mo`, so any still-flagged string shows
   English until reviewed).

## Procedure: add a new language

Example: Simplified Chinese, `zh_CN` (already a stub here; for a brand-new locale, copy the
template — see "Adding a new language to the list of translations" above).

1. Ensure the stub is current: `msgmerge --update --backup=none --previous languages/openporte-zh_CN.po languages/openporte.pot`.
2. Translate every `msgstr` (hand it to a local LLM with the prompt below).
3. Validate + compile: `msgfmt --check languages/openporte-zh_CN.po -o languages/openporte-zh_CN.mo`.
4. Smoke-test in wp-env (switch the site language and check the OpenPorte settings screen).

## LLM-assisted translation

The LLM edits the `.po` file **directly** — that keeps gettext as the single source of truth and
needs no custom tooling. Open the target `.po`, hand its full contents plus the prompt below to a
local model, then replace the file with the model's output and validate with `msgfmt --check`
(which also verifies placeholders via `--check-format`). Work one locale at a time.

### Prompt template

Replace the template keywords:

- <TARGET LANGUAGE>: the new translation language to be created, in plain English (e.g. Xhosa).
  There is only one instance of that template keyword in the prompt.
- <LOCALE>: Follow the POSIX (IEEE 1003.1) notation, which is `language[_territory]`,
  language being the ISO 639-1 (e.g. xh for Xhosa, or fr for French) and the territory
  being ISO 3166-1 (e.g. ZA for South Africa, or CA for Canada). There are two instances of that
  template keyword in the prompt.

Example locales:

- xh_ZA: Xhosa in South Africa
- fr_CA: French in Canada

---

```
You are a professional software localizer translating a WordPress plugin's gettext catalog into
<TARGET LANGUAGE> (locale <LOCALE>, e.g. Simplified Chinese / zh_CN).

The target file to translate is (and refer to after as target_file.po):
languages/openporte-<LOCALE>.po

Make sure you have read the file @docs/agents/i18n.md.

Steps — follow exactly, in order and only for the target_file.po, do not change the other files in this directory::

1. Read the full contents of target_file using your file tool.
2. Produce a translated version of that file, applying the rules below. Some files can be
   partially translated already.
3. Every entry marked `#, fuzzy` (with a `#| msgid "..."` comment showing the previous English
   source) had its English string reworded for 1.28.0; its old <TARGET LANGUAGE> translation is
   kept as a rough starting point. Re-translate it to match the new English, then delete both the
   `fuzzy` flag and the `#| msgid` comment line.
4. Every entry with `msgstr ""` is a brand-new string with no translation yet — translate it.
5. Additionally, scan every remaining entry (not fuzzy, not empty) for a `msgstr` that is just an
   unmodified copy of the English `msgid` — a translation skipped in an earlier pass without being
   flagged. Translate those too. Otherwise, leave already-translated entries untouched.
6. Update the header (the entry with `msgid ""`) in target_file.po:
   - Set `PO-Revision-Date` to `2026-07-23 00:00+0000` (or today's date if you run this later).
   - Set `Last-Translator` to `<AGENT_NAME>-<AGENT_VERSION>:<MODEL_SHORT_NAME> - signed-off by J-C Berthon` (no
     email/angle brackets, replace the placeholders by the real values).
   - Leave every other header field untouched, including `Plural-Forms` — do not add, remove, or
     reformat it.
7. Overwrite target_file.po with the translated content using your file write/edit
   tool. Do NOT just print the result to the console or chat — the file on disk must be modified.
8. If you have shell/bash tool access, run
   `msgfmt --check <target_file.po> -o /dev/null` (replace
   "<target_file.po>" by the real file name) and fix any error it reports
   (syntax or placeholder mismatch) before finishing. If you don't have shell access, skip this
   step.
9. After writing, reply with only: "Translation finished, file <target_file.po> saved." (replace
   "<target_file.po>" by the real file name). Do not paste the file content back to me.

Translation rules:

1. Translate ONLY the `msgstr` values. Never alter a `msgid`, comment, reference line, or flag,
   except: when an entry is marked `#, fuzzy`, correct its `msgstr` and DELETE the `fuzzy` flag.
   Output ONLY the translated `msgstr ""` entry. Do not write introductory text, explanations,
   or Markdown code blocks outside the Gettext structure.
2. Leave these untranslated, exactly as written in the source:
   - Read section "Glossary — terms to preserve verbatim" in file @docs/agents/i18n.md.
   - All URLs.
3. Preserve every placeholder (%s, %d, %1$s, %2$s, …) — same set and the same argument numbers —
   and every HTML tag (<a>, <b>, …) exactly. Reorder them within a sentence only if the target
   grammar requires it; never add or drop one.
4. Honour each `#. translators:` comment — it explains what the placeholders mean.
5. IMPORTANT - Description of the plugin in openporte.php
   This string is part of the plugin header. The WordPress Plugin Handbook *recommends* keeping
   it under 140 characters, because it is displayed in the Plugins screen of the admin. Aim for
   that in the translation too.
   It is a recommendation, not an enforced limit — nothing in Plugin Check or the plugin
   directory rejects a longer one, and plugins well over 140 ship in the directory today. So
   treat it as a target: prefer a natural, idiomatic sentence that runs slightly long over a
   contorted one that fits.
   Count **characters, not bytes**. The guidance is about displayed length, so CJK and Cyrillic
   get the same 140 budget as Latin scripts (verified on the bench: Japanese and Ukrainian
   descriptions display in full).
   You can identify this string by the comment which precede it:
       #. Description of the plugin
       #: openporte.php
6. Be natural and idiomatic in <TARGET LANGUAGE>; use a single consistent register throughout
   (use formal address — e.g. the "vous"/infinitive pattern in French — translated into
   <TARGET LANGUAGE>'s own equivalent). Keep translations concise so they fit in UI controls. Do not
   leave any `msgstr` empty.
7. Keep the file a syntactically valid gettext .po file — same structure, same entry order, same
   headers, only `msgstr` values (and `fuzzy` flags per rule 1) change.
8. IMPORTANT — QUOTATION & ESCAPING RULES:
   - File-level double quotes (`msgstr "..."`) wrapping the string must remain intact.
   - ONLY output double quotes inside the string if they were explicitly escaped (`\"`) in the original `msgid`.
   - NEVER convert standard quotes into regional typographic quotes (e.g., do NOT use »...«, „...“, or “...”).
   - Never introduce new quotation marks into the `msgstr` if none existed in the `msgid`.
9. Some msgids about protecting a specific plugin's forms read "Protect <Plugin Name> forms." —
   but a few instead read "Protect <Plugin Name> submissions." That "submissions" wording is only
   an English-specific workaround for plugins whose own name already contains the word "Forms"
   (Gravity Forms, WPForms, HTML Forms, …), to avoid the awkward repetition "Gravity Forms forms."
   If <TARGET LANGUAGE> does not have that repetition problem — e.g. because its word for "forms"
   differs from the one embedded in the plugin's name, or word order keeps them apart — translate
   the natural way and do not force a literal equivalent of "submissions". Example (German):
   "Gravity Forms-Formulare schützen.", not an awkward "Gravity Forms-Übermittlungen schützen."
10. NO VERBOSE REASONING: Output direct sequence translations immediately without preamble.

Do not ask for confirmation before writing the file. Do not summarize the changes in your reply.
Do not stage nor commit.
```

---

After pasting the model's output back into the file:

```bash
# Validate AND compile in one pass (fuzzy entries are excluded from the .mo):
msgfmt --check languages/openporte-<LOCALE>.po -o languages/openporte-<LOCALE>.mo
```

`msgfmt --check` is the gate: it catches malformed syntax and any placeholder mismatch between
`msgid` and `msgstr`. Fix anything it reports before committing. (Use `-o /dev/null` if you only
want to validate without writing the `.mo`.)
